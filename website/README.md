# blackhole-threats website

This folder is the source of the blackhole-threats documentation site,
<https://netspeedy.github.io/blackhole-threats/>, built with Astro and Starlight. The pages
are Markdown and MDX in `src/content/docs`, and some of them use components that only render on
the site, so read the docs there rather than here. The files in the repository's
[`docs/`](../docs/) folder are pointers to the site, apart from
[`release-and-publishing.md`](../docs/release-and-publishing.md).

The components and styles are the same in every netspeedy docs site and use the `ns-` prefix;
s3ctl's site is the standard they follow. What's particular to blackhole-threats, such as its
name, description, links and footer columns, is in `src/lib/site.ts`. The sidebar groups, their
colours and icons, and which header tab shows which group are defined in `src/lib/sections.ts`
and matched to the sidebar in `astro.config.mjs` by label.

## Working on it

Run these from the repository root:

```bash
make website-install   # npm ci, from package-lock.json
make website-dev       # local server with live reload
make website-build     # production build into website/dist/
make website-check     # every page, the search index, icons, share card and internal links
make website-test      # theme, header, tabs, version menu and an archived line in headless Chrome
make website-capture   # desktop and phone screenshots in both themes into website/.captures/
```

`make website-check` reads `website/dist`, so it always runs after the build. `make
website-test` builds its own copies into `website/.test/`. CI builds with the newest
Node 22 release (`check-latest` in setup-node), since the version a runner has cached
can be older than Astro's minimum, which is in `engines` in `package.json`.

`public/og-image.png`, `public/og-image.svg`, the favicons, the Apple touch icon and
`src/assets/mark.svg` are generated by `make readme-hero` along with the README banner, so edit
`scripts/readme/build_readme_hero.py` rather than the files.

## Versioned docs

Only the latest release line's pages live here. When a new minor ships, the Release Assets
workflow rebuilds the outgoing line from git with `SITE_ARCHIVE=vX.Y`, and the Pages workflows
publish it under `/blackhole-threats/vX.Y/` beside the latest. Never copy pages into per-version
folders, and keep page links root-relative (`/blackhole-threats/...`) so archived builds can
rewrite them. The "Versioned docs" section of
[docs/release-and-publishing.md](../docs/release-and-publishing.md#versioned-docs) has the
details, including how to rebuild an archive by hand.

## How it's published

The Pages root is shared with the signed APT repository, so the site is always deployed together
with it and must not break the `dists/`, `pool/` or key download paths. Links to those files are
absolute URLs, because they aren't part of the build and `make website-check` only follows links
into it.

Publish Signed Debian Repository deploys the site at release time, with the new packages. Deploy
Pages Site runs on every push to `main`, after each of those publish runs and after each stable
Release Assets run: it restores the last published APT snapshot, writes the stable release's tag
and the archive key's fingerprint to a JSON file, builds the latest line with it in
`SITE_METADATA_FILE`, unpacks the archived lines into it, runs `make website-check` over the
result and deploys both. The release-time deploy unpacks the archived lines the same way. Local
and pull request builds have no metadata file, so they show the newest local tag and leave the
fingerprint out. Dependabot checks the npm dependencies here daily and titles its pull requests
`chore:`, so a site update doesn't cut a release.
